# PocketBase migration drift: production disk vs repository (2026-09-11)

Production PocketBase (KVM1) runs from `/opt/buildanddo-pocketbase/pb_migrations`.
A read-only copy of that directory (31 files) was diffed against
`apps/pocketbase/pb_migrations` on the branch
`bits/SRS-BUILDANDDO-LIVE-UTILIZATION-001-rooms-sfu-moq-content` at `86e84e5`
(17 files). Every claim below is labeled VERIFIED (read from disk / command output)
or INFERRED (reasoned from the files).

## Why this matters

PocketBase applies migrations in lexical filename order and records the applied
set by **filename** in its `_migrations` table. Two consequences:

1. A file that references a collection must sort after the file that creates it,
   or a fresh database fails with `failed to load collection <name>`.
2. Renaming a file makes PocketBase treat it as a new migration and apply it
   again. Any file the repository renumbers must therefore be safe to re-run on
   production.

Both consequences drive every decision on this page.

## The ordering defect (VERIFIED)

A new staging instance built from production's own directory fails at
`1788798503_updated_services.js` with `failed to load collection workspace_members`.
The 15 rule edits `1788798503..1788798546_updated_*.js` reference
`@collection.workspace_members`, which is created by
`1788900000_create_workspace_members_rbac.js` - a file that sorts **after** them.
The same defect hits the 3 praxis edits `1788799254/1788799326_updated_praxis_*.js`,
which look up collections created by `1788800000_create_praxis_evidence_fabric.js`.

Production only ever worked because those 18 files were generated by the admin
UI on 2026-09-07 16:28-16:42Z, minutes **after** the create migrations had already
run there. Their numbers are the wall-clock second they were generated, which is
lower than the hand-chosen round numbers (`1788800000`, `1788900000`) of the
migrations they depend on.

`node apps/pocketbase/tools/check_migration_order.mjs <copy-of-production>` reports
exactly this: 37 failures (15 x `workspace_members`, 3 praxis lookups by id, plus
19 layout assertions: wrong last file and the 18 missing `1788950001..18` slots). Against the reconciled repository it reports
`35 migrations, 0 problem(s)`.

### CORRECTION on "5 shared files differ"

`diff -u --strip-trailing-cr` and `git ls-files --eol` (VERIFIED) show that
`1788900000`, `1788910000`, `1788920000` and `1788930000` differ from production
**only by CRLF line endings in the Windows working copy**; the git index holds

drift in those four files. Only `1788800000` has a real difference.

## The one real content difference: 1788800000_create_praxis_evidence_fabric.js

VERIFIED diff (production minus repository): production's copy has
`required: true` on five number fields that the repository leaves optional:

| Collection | Field(s) |
|---|---|
| `praxis_methods` | `community_attempts`, `community_verified_successes` |
| `praxis_pricing` | `amount`, `quantity_value` |
| `praxis_timing` | `duration_value` |

The repository copy carries the comment: PocketBase's `required` validator
rejects a literal `0` as blank for number fields (measured 2026-09-07), and these
are counters that legitimately start at zero. Production discovered the same
defect and fixed it **in the admin UI**, which is exactly what the three
production-only files `1788799254_updated_praxis_methods.js`,
`1788799326_updated_praxis_pricing.js` and `1788799326_updated_praxis_timing.js`
record: each one's `up()` sets `required: false` on precisely these five fields and
its `down()` sets `required: true` (VERIFIED by reading the files).

**Decision: keep the repository version.** This is not the default "adopt
production disk" rule, and it is not the "production is a strict subset" exception
either, so the reasoning is spelled out:

- The file will never run on production again: `1788800000_create_praxis_evidence_fabric.js`
  is already recorded in its `_migrations` table under that name. Its content only
  affects fresh installs.
- On a fresh install the end state is identical either way: the create migration
  followed by the imported `1788950016..18` yields `required: false` on all five
  fields. Adopting production's text would deliberately re-create a known bug in
  the create step only for a later migration to undo it.
- Production's effective schema (after its own admin-UI fix) equals the repository's
  create output, so the repository is already the truth for the *result*; the
  imported praxis files preserve production's *history* of getting there.

If the parent seat prefers byte fidelity to production over this reasoning, the
production text is at `%TEMP%\kvm1_migrations\1788800000_create_praxis_evidence_fabric.js`
and swapping it in changes nothing observable on any database.

### Why the hard-coded `pbc_` ids are safe on a fresh install (VERIFIED)

The repository's create migrations do not set collection ids, so a fresh install
lets PocketBase generate them. Measured against production's ids:
`"pbc_" + crc32("base" + name)` reproduces every one of the 18 (e.g.
`crc32("baseservices") = 863811952`, `crc32("basepraxis_methods") = 2463497436`),
and field ids are `type + crc32(name)` (e.g. `number1300308547` = `community_attempts`).
Both derivations are deterministic, so the ids the admin UI baked into these files
resolve to the same collections and fields on any database created from this
repository. `check_migration_order.mjs` asserts this for every `pbc_` lookup.

### Renumbering

`1788950001..1788950018` preserves production's relative order, sorts after
`1788900000` (RBAC) and `1788940000_*` (last repo migration before the block), and
before `1789000000_extend_workspace_operations.js` and `1789100000_ocn_seat_users.js`.
Each imported file carries a header naming its original production filename, the
reason for renumbering, and the re-apply-on-production consequence.

Nothing was refused: no imported migration creates records, adds unique indexes,
or does anything that could collide on re-apply.

## What happens on the next production migrate (INFERRED)

Production's `_migrations` table holds the 31 original names. Applying this
repository's directory will run, in order: `1788940000_*` (2), `1788950001..18`
(idempotent re-applies), `1789000000`, `1789100000`. The 18 original-named files
stay recorded until the deploy replaces the directory; once replaced, PocketBase
lists them as applied-but-missing, which is harmless (it never reverts what it
cannot find). Fresh installs (staging) run all 35 in one clean pass.

## Guard

`npm run pb:check-migrations` (in `apps/pocketbase`) runs
`tools/check_migration_order.mjs`: parses every filename, asserts the layout
(last file, imported block present, shared stamps noted), and for every
`@collection.<name>` reference and `findCollectionByNameOrId(...)` lookup asserts
the collection is created by an earlier-or-same file (or ships with PocketBase).
Exit 1 on any failure.
